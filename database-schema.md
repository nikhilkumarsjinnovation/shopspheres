# ShopSphere Phase 1 — Database Schema & Security Architecture

**Role:** Lead Database Administrator (DBA)  
**Platform:** Supabase PostgreSQL 15+  
**Naming Convention:** Strict `snake_case` for all table, column, enum, and index identifiers  
**Status:** Approved for Production Migration  

---

## 1. Architectural Overview & Conventions

* **Schema Isolation:** All application tables reside in the `public` schema and link to Supabase's managed `auth.users` authentication catalog.
* **Identifier Standard:** All table names (`users`, `products`, `orders`, `order_items`) and column names strictly adhere to lowercase `snake_case`.
* **Primary Keys:** Standardized on `UUID` (`gen_random_uuid()`) for decentralized scalability and security against sequential enumeration attacks.
* **Timestamp Standard:** All timestamps utilize `TIMESTAMPTZ` (UTC) with default value `NOW()`.
* **Currency Precision:** Monetary values use `NUMERIC(10, 2)` with non-negative check constraints (`CHECK (column >= 0)`).
* **Row-Level Security (RLS):** Enabled on 100% of tables with strict default-deny policies.

## 3. Table Definitions & Column Specifications

### 3.1 `users` Table
Handles user profile records, role assignments, and links directly to `auth.users`.

| Column Name | Data Type | Constraints | Default | Description |
| :--- | :--- | :--- | :--- | :--- |
| `id` | `UUID` | `PRIMARY KEY`, `REFERENCES auth.users(id) ON DELETE CASCADE` | None | Direct foreign key binding to Supabase auth record. |
| `email` | `TEXT` | `NOT NULL`, `UNIQUE` | None | User email address synchronized from auth payload. |
| `full_name` | `TEXT` | Nullable | `NULL` | Customer or seller business representative display name. |
| `avatar_url` | `TEXT` | Nullable | `NULL` | Public asset URL for avatar or shop logo. |
| `role` | `user_role` | `NOT NULL` | `'customer'` | Authorization role (`customer`, `seller`, `admin`). |
| `is_active` | `BOOLEAN` | `NOT NULL` | `TRUE` | Administrative status flag for account deactivation. |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL` | `NOW()` | Record creation timestamp. |
| `updated_at` | `TIMESTAMPTZ` | `NOT NULL` | `NOW()` | Record last modification timestamp. |

#### DDL Statement:
```sql
CREATE TABLE public.users (
  id UUID PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
  email TEXT NOT NULL UNIQUE,
  full_name TEXT,
  avatar_url TEXT,
  role user_role NOT NULL DEFAULT 'customer',
  is_active BOOLEAN NOT NULL DEFAULT TRUE,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

## 5. Row-Level Security (RLS) Policies

### 5.1 RLS Activation
```sql
ALTER TABLE public.users ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.products ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.orders ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.order_items ENABLE ROW LEVEL SECURITY;
```

---

### 5.2 `users` Table RLS

#### Plain English Logic:
1. **Self-Profile Read:** Any authenticated user can read their own user record (`auth.uid() = id`).
2. **Public Identity Read:** Authenticated users can view public profile details (name, avatar, role) of sellers to verify storefront authenticity.
3. **Self-Profile Update:** Users can update their own personal info (`full_name`, `avatar_url`), but are strictly forbidden from modifying their own `role` or `is_active` status.
4. **Admin Complete Visibility:** Platform administrators (`role = 'admin'`) have global read and update permissions on all user records to audit platform participants and enforce suspensions.

#### SQL Policy Statements:
```sql
-- Helper function to check admin role
CREATE OR REPLACE FUNCTION public.is_admin()
RETURNS BOOLEAN LANGUAGE sql SECURITY DEFINER AS $$
  SELECT EXISTS (
    SELECT 1 FROM public.users
    WHERE id = auth.uid() AND role = 'admin'
  );
$$;

-- Helper function to check seller role
CREATE OR REPLACE FUNCTION public.is_seller()
RETURNS BOOLEAN LANGUAGE sql SECURITY DEFINER AS $$
  SELECT EXISTS (
    SELECT 1 FROM public.users
    WHERE id = auth.uid() AND role = 'seller'
  );
$$;

-- 1. Read: Users read own profile OR Admins read all OR Read public sellers
CREATE POLICY "users_read_policy" ON public.users
  FOR SELECT
  TO authenticated
  USING (
    id = auth.uid()
    OR public.is_admin()
    OR role = 'seller'
  );

-- 2. Update: Users update own profile (role updates prevented via trigger or column restrictions)
CREATE POLICY "users_update_policy" ON public.users
  FOR UPDATE
  TO authenticated
  USING (
    id = auth.uid() OR public.is_admin()
  )
  WITH CHECK (
    id = auth.uid() OR public.is_admin()
  );
```

### 5.3 `products` Table RLS

#### Plain English Logic:
1. **Customer Catalog Browsing:** Anyone (including unauthenticated visitors and logged-in customers) can ONLY read products that have been reviewed and approved by administrators (`approval_status = 'approved'`).
2. **Seller Product Insertion:** Only authenticated users with the `seller` role can insert new products, and they must assign `seller_id` equal to their own authenticated user ID (`auth.uid()`).
3. **Seller Lifecycle Visibility & Mutation:** Sellers can view and update their own products regardless of status (`approval_status = 'pending'`, `'approved'`, or `'rejected'`). They cannot alter products belonging to other merchants.
4. **Admin Global Oversight & Approval Mutation:** Admins can view all products and update any product's `approval_status` (e.g., approving or rejecting submissions).

#### SQL Policy Statements:
```sql
-- 1. Read: Public read access for approved products; Sellers read own; Admins read all
DROP POLICY IF EXISTS "products_read_policy" ON public.products;
CREATE POLICY "products_read_policy" ON public.products
  FOR SELECT
  TO public
  USING (
    approval_status = 'approved'
    OR (auth.uid() IS NOT NULL AND seller_id = auth.uid())
    OR public.is_admin()
  );

-- 2. Insert: Only authenticated sellers can create products under their own seller_id
CREATE POLICY "products_insert_policy" ON public.products
  FOR INSERT
  TO authenticated
  WITH CHECK (
    public.is_seller()
    AND seller_id = auth.uid()
  );

-- 3. Update: Sellers can only modify their own products; Admins have emergency audit update
CREATE POLICY "products_update_policy" ON public.products
  FOR UPDATE
  TO authenticated
  USING (
    (seller_id = auth.uid() AND public.is_seller())
    OR public.is_admin()
  )
  WITH CHECK (
    (seller_id = auth.uid() AND public.is_seller())
    OR public.is_admin()
  );

-- 4. Delete: Only product owner seller or platform admin can remove a product
CREATE POLICY "products_delete_policy" ON public.products
  FOR DELETE
  TO authenticated
  USING (
    (seller_id = auth.uid() AND public.is_seller())
    OR public.is_admin()
  );
```

### 5.4 `orders` Table RLS

#### Plain English Logic:
1. **Customer Order Creation:** Any authenticated user can insert an order where `customer_id` matches their authenticated user ID (`auth.uid()`).
2. **Customer Order Visibility:** Customers can view and track orders that they personally placed (`customer_id = auth.uid()`).
3. **'Gift for Friend' Delayed Reveal Logic:** In gift orders (`is_gift = TRUE`), the recipient (matching `recipient_email` with current user's email) is allowed to read order tracking **only if and when** the current time (`NOW()`) is greater than or equal to `gift_reveal_date`. Prior to that release timestamp, the order is completely invisible to the recipient to maintain the surprise. The purchasing customer retains uninterrupted, real-time access throughout.
4. **Admin Global Health Oversight:** Admins possess read access to platform-wide orders to compute platform health metrics (GMV, order volume, transaction rates) and troubleshoot fulfillment issues.

#### SQL Policy Statements:
```sql
-- 1. Insert: Authenticated users can insert orders where they are the customer
CREATE POLICY "orders_insert_policy" ON public.orders
  FOR INSERT
  TO authenticated
  WITH CHECK (
    customer_id = auth.uid()
  );

-- 2. Read: Customer owner, Admin audit, or Recipient if gift reveal date has passed
CREATE POLICY "orders_read_policy" ON public.orders
  FOR SELECT
  TO authenticated
  USING (
    -- Case A: Purchasing customer
    customer_id = auth.uid()
    -- Case B: Admin platform health inspection
    OR public.is_admin()
    -- Case C: Gift recipient after reveal threshold
    OR (
      is_gift = TRUE
      AND recipient_email = (SELECT email FROM public.users WHERE id = auth.uid())
      AND gift_reveal_date IS NOT NULL
      AND NOW() >= gift_reveal_date
    )
  );

-- 3. Update: Admins can update order status; Customers can cancel pending orders they created
CREATE POLICY "orders_update_policy" ON public.orders
  FOR UPDATE
  TO authenticated
  USING (
    customer_id = auth.uid()
    OR public.is_admin()
  )
  WITH CHECK (
    customer_id = auth.uid()
    OR public.is_admin()
  );
```

### 5.5 `order_items` Table RLS

#### Plain English Logic:
1. **Customer Line Item Read:** Customers can view line items belonging to orders they placed.
2. **Seller Order Fulfillment Read:** Sellers can view line items where `seller_id = auth.uid()`. This ensures merchants can view and fulfill orders containing their merchandise without gaining access to other sellers' line items or unrelated customer orders.
3. **Admin Comprehensive Read:** Admins can view all line items for aggregated GMV calculations and dispute reconciliation.

#### SQL Policy Statements:
```sql
-- 1. Read: Accessible to purchasing customer, fulfilling seller, or admin
CREATE POLICY "order_items_read_policy" ON public.order_items
  FOR SELECT
  TO authenticated
  USING (
    -- Customer who owns parent order
    EXISTS (
      SELECT 1 FROM public.orders
      WHERE orders.id = order_items.order_id
      AND orders.customer_id = auth.uid()
    )
    -- Seller responsible for fulfilling this item
    OR seller_id = auth.uid()
    -- Platform Admin
    OR public.is_admin()
  );

-- 2. Insert: Allowed via database transactional checkout routines or authenticated order creation
CREATE POLICY "order_items_insert_policy" ON public.order_items
  FOR INSERT
  TO authenticated
  WITH CHECK (
    EXISTS (
      SELECT 1 FROM public.orders
      WHERE orders.id = order_items.order_id
      AND orders.customer_id = auth.uid()
    )
  );
```

## 6. Automated Database Triggers

### 6.1 Automatic `updated_at` Timestamp Synchronization
```sql
CREATE OR REPLACE FUNCTION public.set_updated_at_column()
RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at = NOW();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER update_users_updated_at
  BEFORE UPDATE ON public.users
  FOR EACH ROW EXECUTE FUNCTION public.set_updated_at_column();

CREATE TRIGGER update_products_updated_at
  BEFORE UPDATE ON public.products
  FOR EACH ROW EXECUTE FUNCTION public.set_updated_at_column();

CREATE TRIGGER update_orders_updated_at
  BEFORE UPDATE ON public.orders
  FOR EACH ROW EXECUTE FUNCTION public.set_updated_at_column();
```

### 6.2 New Auth User Provisioning Hook
Synchronizes newly registered Supabase Auth identities into `public.users` with their designated role:
```sql
CREATE OR REPLACE FUNCTION public.handle_new_auth_user()
RETURNS TRIGGER AS $$
DECLARE
  assigned_role user_role := 'customer';
BEGIN
  -- Extract role from metadata if provided during sign-up
  IF NEW.raw_user_meta_data->>'role' IN ('customer', 'seller') THEN
    assigned_role := (NEW.raw_user_meta_data->>'role')::user_role;
  END IF;

  INSERT INTO public.users (id, email, full_name, role)
  VALUES (
    NEW.id,
    NEW.email,
    COALESCE(NEW.raw_user_meta_data->>'full_name', ''),
    assigned_role
  );
  RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

CREATE TRIGGER on_auth_user_created
  AFTER INSERT ON auth.users
  FOR EACH ROW EXECUTE FUNCTION public.handle_new_auth_user();
```
